# JuMACS

**Jülich Multi-source Atmospheric Climatology System** provides monthly zonal atmospheric reference climatologies derived from internally consistent chemistry-climate simulations. The default is **1985–2014 inclusive** (30 years), with `nominal_reference_year=2000` as an epoch label. It does not equate trend-sensitive concentrations with year-2000 abundances; it applies no detrending, normalization, bias correction, satellite adjustment, model weighting, or ensemble averaging.

```text
CCMI refD1 ──→ monthly zonal series ──→ native climatology ──→ application-grid remap ──→ application NetCDF
WACCM-X ────→ monthly zonal series ──→ native climatology ──→ optional upper-atmosphere extension
```

GEOSCCM and EMAC are independent CCMI-2022 refD1 primary model sources. The pressure-grid application product remaps **each CCMI model separately** and can extend it upward with WACCM-X. The older `compact` command produces a separate altitude-grid product. There is no GEOSCCM–EMAC average. Native model products remain unchanged. Satellite climatologies are evaluation data only. They never fill cells or change production climatologies. Direct satellite fusion is inappropriate here because observing periods, instrument biases, retrieval characteristics, trends in long-lived gases, and vertical/temporal overlap differ.

All CCMI-2022 refD1 records are published under the [Open Government Licence v3](http://www.nationalarchives.gov.uk/doc/open-government-licence/version/3/); cite the dataset record listed in each `config/models/<model>.yaml`.

The WACCM-X archive publishes ready-made monthly zonal `_zm.nc` files; JuMACS uses these directly. Its file `time` coordinate is the **next month's first day**, while `time_bnds` and the filename identify the represented month. The reader labels samples with the interval midpoint, so `1985-01_zm.nc` contributes to January 1985. Its 126 hybrid midpoint levels use `p=hyam*P0+hybm*PS`. GEOSCCM full 3-D fields use `p=a*p0+b*ps` (72 levels); EMAC uses `p=ap+b*ps` (90 levels). CCMI `AmonZ` chemistry uses native pressure coordinates in Pa. Actual valid coverage is calculated from finite species values and pressure, not inferred from model top. Altitude comes from native geopotential height where coordinates align, particularly for WACCM-X. Other levels receive a labelled `7 ln(101325/p)` km scale-height estimate, which is unreliable above roughly 80 km.

`config/models/` is the source registry: one YAML file per CCMI-2022 refD1 model plus `config/waccmx.yaml` for the separate whole-atmosphere source. GEOSCCM, EMAC and the nine other CCMI refD1 models whose CEDA identifiers were verified live against the archive and catalogue (ACCESS-CM2-Chem, CCSR-NIES-MIROC32, CESM2-WACCM, CMAM, CNRM-MOCAGE, IPSL-CM6A-ATM-LR-REPROBUS, NIWA-UKCA2, SOCOL, UKESM1-StratTrop) are `status: ready` with `archive_inventory` and `download` enabled. MIROC-ES2H stays `status: unresolved`: it has no refD1 contribution in the archive or catalogue (its collection publishes refD2 and sensitivity experiments only), so no identifier was guessed. Identifiers are never guessed; each ready entry carries a comment recording the dataset record contact, publication year and verification date. SOCOL publishes a non-standard layout (member directories `gn`/`gnz`, grid directory `r1i1p1f1`) and UKESM1-StratTrop timestamps monthly files `YYYYMMDD-YYYYMMDD`; the inventory walker accepts both forms. Each source also declares explicit `capabilities` (`archive_inventory`, `download`, `zonal_processing`, `climatology`, `compact_waccmx`); commands such as `compact` accept only models whose capability is enabled, and unregistered capability defaults to false. `config/species.yaml` defines the canonical species list and groups used by the inventory and coverage matrices. `inspect --model all` writes model-specific archive inventories plus `products/comparison/variable_matrix.csv` (per-model `<model>_status` of `ok`/`absent`/`no_mapping`/`unresolved`/`not_inspected` and `<model>_available`) and `products/comparison/native_variables.csv` across the full registry. `jumacs summary` then works fully offline on the local inventories and regenerates `products/comparison/model_summary.csv` (per-model file counts, time range, Amon/AmonZ variable counts, mapped-species counts), `products/comparison/species_summary.csv` (per-species model coverage, AmonZ-only counts, WACCM-X availability) and `products/comparison/summary.md` (overview, coverage, per-group chemistry richness, Amon/AmonZ split, gaps, and a separate WACCM-X section). The nine newly verified CCMI models publish the standard CCMI native variable names and their `variables:` mappings follow the already-mapped GEOSCCM/EMAC names. The native-variable report keeps source fields that exist only in a monthly multi-variable file, such as WACCM-X native species, separate from the canonical species list until a mapping is deliberately configured. Missing species remain missing. No family sum replaces an individual gas. Neither CCMI refD1 source has a monthly SF6 directory, and the inspected WACCM-X zonal file has no three-dimensional SF6 field. WACCM-X zonal files contain many variables together, so selecting one variable for download still selects the monthly multi-variable files.

## Workflow on JUWELS

From the repository and HPC project root `/p/data1/slmet/model_data/jumacs`:

```bash
source scripts/python_setup.sh
python -m pytest -q
jumacs inspect --model all            # archive contents, variable mappings, readiness
jumacs download --model CMAM --start-year 1985 --end-year 2014  # size plan only
jumacs build --model CMAM --start-year 1985 --end-year 2014     # zonal series + climatology + report
jumacs quicklook --model CMAM --start-year 1985 --end-year 2014
jumacs build --model CMAM,SOCOL --start-year 1985 --end-year 2014   # several models in one call
jumacs build --model all              # every ready model with validated zonal processing
jumacs application --model SOCOL --start-year 1985 --end-year 2014  # pressure-grid product
jumacs browse --start-year 1985 --end-year 2014  # static site from existing application products
jumacs download --model GEOSCCM --all-files  # complete-archive mirror plan (all families/members, latest versions)
jumacs download-audit  # audit all mirror plans, write products/comparison/download_plan_summary.{csv,md}
```

`build` takes one model (or list, or `all`) as the unit of work: it reads the variables from `config/models/<model>.yaml`, reuses any existing `data/processed/.../VARIABLE_monthly_zonal.nc`, builds the missing monthly zonal series, computes the climatology, and prints one JSON report per model (`zonal_built`, `zonal_reused`, `skipped` with reasons, `variables_processed`, `product`, `conventions`, `variables_in_product`, the native `vertical` grid actually written, the `application_pressure_grid` that combination will apply, per-variable `checks`, `ok`). Variables without downloaded data, or whose zonal series does not overlap the requested period, are skipped and named in the report instead of failing the run; the run fails only when no variable is processable. Registry mappings are never bypassed: a model must combine `status: ready` with `capabilities.zonal_processing: true`, so explicit `--variable` does not unlock unvalidated coordinate mappings. The per-step commands (`zonal`, `climatology`, `zonal-smoke`, `validate-raw`, `coordinate-audit`, `post-download-audit`) remain available and are labelled advanced in `jumacs --help`.

IPSL-CM6A-ATM-LR-REPROBUS, CCSR-NIES-MIROC32 and NIWA-UKCA2 now use their published AmonZ pressure-level fields for 3D climatologies and Amon fields for 2D quantities. For NIWA, `epfy` and `epfz` are omitted from the default build because their latitude grid differs from the other variables; `c2h6` is omitted because only its hybrid-height Amon form is archived and its pressure needs the separate `pa` field. These mappings remain in the registry, but the default build does not silently misplace them.

`scripts/python_setup.sh` loads the Python module, creates/activates `.venv` and installs JuMACS with the test extra; re-run it with `source scripts/python_setup.sh --update` to refresh pip, JuMACS and dependencies.

The installed command is `jumacs` (editable install from the setup script); `python3 -m jumacs.cli` also works with manually loaded modules and `PYTHONPATH="$PWD/src"`. `--model` accepts any registered model name or `all`. The `download` command is plan-only: it prints and saves a size estimate without transfer. `download --model MODEL --all-files` plans a complete-archive mirror instead of the mapped-species window: every file in the model's inventory across all families and members of the configured archive trees, superseded versions deduplicated to the latest release; `download-audit` rebuilds those mirror plans for every available source and writes the audit to `products/comparison/download_plan_summary.csv`/`.md` (WACCM-X reported separately; unresolved models excluded).

Transfers need general Internet access, which JUWELS **compute nodes do not have**; there is therefore no download wrapper in `scripts/slurm/`. Execute a reviewed plan only where Internet egress works: with `python3 scripts/archive_download.py --model MODEL --execute` (or `--all`), which auto-discovers manifests in `products/manifests/` and needs only `requests` — run it on **JUDAC** (preferred for bulk transfer) or on a **JUWELS login node** (`jumacs download --model MODEL --execute` or `make download-execute MODEL=...` remain available for small selections). Keep bulk work on JUDAC and mount the shared tree over SSHFS (`~/jumount`) when copying from JUDAC. Heavy processing still runs through Slurm, not on the login node, and Slurm jobs must not fetch data at run time:

```bash
sbatch -A YOUR_ACCOUNT scripts/slurm/build.sh GEOSCCM 1985 2014   # zonal + climatology
sbatch -A YOUR_ACCOUNT scripts/slurm/build.sh EMAC 1985 2014
sbatch -A YOUR_ACCOUNT scripts/slurm/compare.sh 1985 2014
sbatch -A YOUR_ACCOUNT scripts/slurm/plot_catalog.sh
sbatch -A YOUR_ACCOUNT scripts/slurm/plot_comparisons.sh
sbatch -A YOUR_ACCOUNT scripts/slurm/compact.sh GEOSCCM
sbatch -A YOUR_ACCOUNT scripts/slurm/compact.sh EMAC
```

`scripts/slurm/build.sh` is the normal submission path because it wraps `jumacs build`: it reuses existing monthly zonal intermediates, builds only what is missing, and validates the climatology afterwards. The per-stage wrappers (`scripts/slurm/zonal_model.sh`, `zonal_array.sh`, `climatology.sh`, `submit_processing.py`) and the matching `jumacs zonal` / `jumacs climatology` commands, `make zonal MODEL=...` and `make climatology MODEL=...` are advanced entry points for re-running one stage after a failed build or for debugging a single variable; running `climatology.sh` alone skips the coverage checks that `build` performs.

For WACCM-X, first inspect and plan download, then transfer the selected monthly `_zm.nc` files from JUDAC. Afterward, submit zonal tasks by variable and its climatology. `make inspect`, `make test`, `make download MODEL=...` (plan), `make download-execute MODEL=...`, `make build MODEL=...`, `make zonal MODEL=...`, `make climatology MODEL=...`, `make coverage MODEL=...`, and `make compare` are shortcuts. The default 1985–2014 reference period is defined only in `config/climatology.yaml`; the Makefile and CLI omit year flags when unset and read that file, and a model YAML may add a `period:` override. `--start-year` and `--end-year` allow any covered inclusive period. The monthly zonal series remain intact.

## Post-download audit

After a transfer and before enabling any processing, run the offline post-download audit. It reads only local raw files and manifests — no CEDA access, no re-planning, no downloads, no config changes — and opens at most a few small representative files per model (metadata plus tiny slices; no hashing, no full-field reads):

```bash
jumacs validate-raw --model all       # transfer integrity: completeness, .part strays, signatures, readability
jumacs coordinate-audit --model all   # conventions: grid, vertical coordinate, time, reader compatibility
jumacs post-download-audit --model all  # both stages in one run
```

`validate-raw` reports per model `ok`, `incomplete`, `invalid`, `not_downloaded` or `not_applicable` (manifest vs. disk counts, leftover `.part` files, NetCDF/HDF5 signatures, time decoding, size tolerance against manifest listing estimates) and writes `products/diagnostics/raw_validation/MODEL.json` plus `products/comparison/raw_validation.{csv,md}`. `coordinate-audit` classifies each model's observed horizontal grid (regular, curvilinear, already zonal, partial longitude), vertical coordinate (pressure levels, hybrid sigma-pressure/hybrid height with observed vs. inferred `formula_terms`, pure sigma, altitude) and time handling, and grades reader compatibility `supported_now`, `small_mapping_change`, `reader_extension_needed` or `unsupported` with machine-readable reasons and a `main_action` per model; outputs are `products/diagnostics/coordinate_audit/MODEL.json` and `products/comparison/coordinate_audit.{csv,md}`. Treat `incomplete`/`invalid` or any `reader_extension_needed` as a gate: fix the transfer or extend the reader before submitting zonal/climatology jobs. The audit is descriptive evidence; it never edits `config/models/*.yaml` or enables processing steps.

## Products

**Application products use one project-wide pressure axis** defined in `config/climatology.yaml`: **124 levels** from `100000` Pa at the surface to `0.002` Pa near 120 km, uniform in `log10(pressure)` with **about 16 levels per decade** (123 intervals over 7.7 decades), so adjacent levels differ by a constant factor of about 1.16. Logarithmic spacing is the appropriate choice because pressure spans nearly eight decades over that range and a constant relative spacing keeps resolution meaningful throughout; at a representative scale height of about 7 km that factor corresponds to roughly **1 km** of vertical spacing, which preserves the vertical structure the intended JURASSIC radiative-transfer/retrieval and MPTRAC transport/chemistry applications need while 124 levels stay modest in compute and storage for monthly zonal climatologies. This is an application grid, not a claim that every atmospheric feature is fully resolved, and it is not the axis the climatology products are stored on. Endpoints are exact and intermediate levels fall where the resolution puts them, so `100`, `10` and `1` hPa are grid-*nearest* pressures rather than grid points. `0.002` Pa is approximately 120 km in an isothermal 7 km scale-height estimate; true altitude at that pressure varies with the state, latitude and season, so the grid is defined by pressure and never by altitude. Wherever the grid is applied it is stored in Pa, in descending order, as the coordinate `pressure` (`standard_name=air_pressure`, `positive=down`). The endpoints plus `intervals_per_decade` are the only definition — commands, plots and tests read the levels through `config.vertical_grid()`, which derives the count from the requested resolution and refuses a missing section, non-`Pa` units, a written-down level list, non-positive or non-monotonic pressures, or a resolution below one interval per decade — so changing the resolution means editing those three numbers and rebuilding. The grid is applied **when an application product is built**, never inside a native single-model product: `cf.assert_product` refuses an individual climatology whose level axis already sits on it and says to rebuild it with `jumacs climatology`, because the monthly zonal intermediates are retained, so a native product can never be mistaken for a combined one and nothing is resampled silently.

**Native statistics are not interpolated during `build`.** The monthly zonal series keeps the vertical grid of its model and the calendar-month `mean`, population `sigma`, `minimum` and `maximum` are accumulated on those native levels, so the vertical step is left out of the pipeline entirely rather than performed twice: the global attributes state it (`vertical_interpolation` begins `none; every statistic is computed on the native vertical levels of the model`, `vertical_extrapolation` begins `none; a level the model does not reach simply does not exist here`), and a level a model does not reach simply has no row in that file. The application builder later remaps those native statistics once onto the configured grid. `n_years` is a true coverage count on the native level, and `finite_fraction` in the build report quantifies what is missing rather than filling it. Each `<variable>_mean` field records the vertical treatment of its own source: `on_application_pressure_grid: "false"`, `vertical_treatment: climatological statistics on the native vertical levels of the model`, `native_level_dimension`, `native_level_count`, `native_vertical_coordinate`, `native_pressure_units` and `native_pressure_kind` — `coordinate` when the level coordinate itself carries pressure in Pa, `profile` when a `(time, level, lat)` `air_pressure` field does, as on hybrid grids — plus the observed `native_pressure_min_pa`/`native_pressure_max_pa`. A model that keeps two unrelated vertical grids under the *same* source level name — GEOSCCM carries its chemistry on 39 pressure levels and its dynamics on 72 hybrid levels and calls both dimensions `lev` — is published with one dimension per grid instead of a merged union of 111 levels that would turn every field of the other grid into rows of NaN: the first grid keeps the source name and the others are numbered `lev_2`, `lev_3`, ..., with nothing resampled and the source name still in `native_vertical_coordinate`. A grid is recognised by the pressures of its levels, never by its name and never by its level count alone: two grids of the same length whose pressures differ are two grids, a grid whose pressures agree within a relative tolerance is one grid whatever its source name, and the *representation* of the pressure belongs to the identity of a grid too: a grid whose levels are a fixed pressure and a grid whose levels move are two grids even when their pressures agree level by level, because a CF dimension coordinate applies to every variable that shares its dimension, so publishing a pressure-valued `lev` coordinate over a variable whose pressure is a `(time, level, lat)` profile would state a pressure for it that is not its pressure. The coordinate grid keeps the source name and the profile grid takes the next number, so the split is decided by what the pressure is, not by which variable was read first. `vertical_level_counts` lists every grid of the product (`lev=39; lev_2=72`) while `vertical_level_count` remains the deepest one, and the coordinate of a grid whose pressure lives only in a field is the plain level index of the model (`units: 1`, `positive: down`) with that field published alongside it as `air_pressure_<dimension>` and named in the field's `pressure_field`; a variable whose levels come from the coordinate instead names it in `pressure_coordinate`, and a field never names both. An index coordinate carries `units: 1`, no `standard_name`, and a `comment` that points at the field holding the pressure of its levels, and when two grids share one source name the coordinate of each says in its own `comment` that the variables of the other take their pressure from their own dimension — the one place a reader cannot miss it, because a shared name is otherwise easy to read across. Every part is renamed and pinned to the canonical coordinate of its grid **before** the fields are merged, so an equal level name hiding two representations can never be unioned into one axis of mixed rows, and a part whose level count disagrees with the grid it was registered on is refused by variable name. Each `<variable>_mean` also carries `native_source_level_dimension`, the name that grid had in the model, which for the second and later grids differs from the published `native_level_dimension`. Two-dimensional fields (tropopause pressure and height, and similar scalar-per-column fields) keep their own `time, lat` shape, get no vertical dimension, and are labelled `vertical_treatment: two-dimensional field kept without a vertical dimension`. Where the application grid *is* applied — application products and the coverage matrix — the vertical rules are shared and strict: interpolation is linear in `log(p)` per latitude column and per calendar month, **never extrapolates**, and treats a non-finite or non-positive pressure as a barrier that is dropped rather than bridged, so an internal gap in a model's published mask stays a gap and a column with fewer than two valid points is NaN.

Each `data/processed/MODEL/.../VARIABLE_monthly_zonal.nc` retains time, latitude, native level, native units, source file names, and model identity, and the climatology product is written on those same native levels — nothing is regridded anywhere in the build. `jumacs climatology --model GEOSCCM` (and the climatology step of `jumacs build`) writes **exactly one file per model and period**: `products/climatology/GEOSCCM/jumacs_geosccm_refd1_climatology_1985-2014.nc`. There are no per-variable files any more, and no groups — one ordinary NetCDF dataset holds every processed variable as `<variable>_mean`, `<variable>_sigma`, `<variable>_minimum`, `<variable>_maximum`, `<variable>_n_years`, so a single file can be opened once and indexed by species.

The file follows **CF-1.13** (`Conventions` attribute) and, most importantly, uses a **climatological time axis** instead of a fake twelve-month time series. `time` is a float64 coordinate variable with `units = "days since 2000-01-01"` (the configured nominal reference year), `calendar = "gregorian"`, `axis = "T"`, `standard_name = "time"` and `climatology = "climatology_bounds"`; the twelve cells are the twelve calendar months, not twelve dates. `climatology_bounds(time, nv)` brackets each cell with the start and end of that month taken from a **common non-leap year**, so February always has 28 days and the annual cycle has exactly twelve intervals; the bounds variable carries the same `units`/`calendar` and deliberately no fill value. Which statistic each field holds is stated the CF way, in `cell_methods`, so no statistic name is invented inside `standard_name`: `<variable>_mean` is `longitude: mean time: mean within years time: mean over years`, `<variable>_sigma` uses `time: standard_deviation over years`, `<variable>_minimum`/`<variable>_maximum` use `time: minimum over years`/`time: maximum over years`, and `<variable>_n_years` is `longitude: mean time: sample_size over years` with `units = "1"` and no `standard_name` (it is a count). `long_name` spells the statistic out in words, e.g. `"Ozone mixing ratio: climatological standard deviation"`.

`standard_name` is published **only when the source name is genuinely CF**: `cf.valid_standard_name` accepts a curated list plus the regular `mole_fraction_of_*_in_air`/`mass_mixing_ratio_of_*_in_air` pattern, and drops anything else so the field keeps an accurate `long_name` rather than a fabricated standard name. No CF table is downloaded and no name is invented. Where an archive names its fields with nothing CF-like — WACCM-X keeps raw CAM-chem names such as `O3`, `T`, `PS`, `OMEGA` — the correspondence is declared explicitly in a `standard_names:` section of that model's configuration (`config/waccmx.yaml`), and `cf.curated_standard_name` publishes such a name **only when the field's `units` match what that CF name requires** (`mol mol-1` for a mole fraction, `K` for `air_temperature`, `m2 s-2` for `geopotential_height`, which is why WACCM-X `Z3`, stored in metres, stays unnamed). Each published name records its origin in `standard_name_source`, `archive` or `config`. All three-dimensional fields are ordered `(time, <native level>, lat)`, where `<native level>` is the level coordinate of the model itself — float64, `units = "Pa"`, `standard_name = "air_pressure"`, `positive = "down"`, `axis = "Z"` when the model publishes pressure on that coordinate, otherwise a plain level dimension whose pressure is published as a separate `(time, <native level>, lat)` `air_pressure` field in Pa — and `lat` (`degrees_north`, `axis = "Y"`, float64); two-dimensional fields are `(time, lat)`. Statistics have fixed storage: `float32` fields with a NaN fill value and compressed, `int16` for `n_years`, float64 coordinates. Model-wide provenance (source dataset/archive, experiment, institution, coverage, period, `reference_period_years`, `nominal_reference_year`, grid description and level count, the interpolation and extrapolation rules, missing-value policy, `variable_count`, processing history) is recorded **once as global attributes** rather than repeated per variable; `bias_correction`, `trend_correction` and `model_combination` are `none`. Global `time_coverage_start`/`time_coverage_end` delimit the **climatological period** (for the reference product `1985-01-01` and `2014-12-31`), because that is the interval the file describes; the usually longer span of the underlying monthly series is kept separately in `source_time_coverage_start`/`source_time_coverage_end` as evidence of the sampling behind the means. The writer refuses a product whose coverage attributes disagree with `climatology_period` and `reference_period_years`.

The writer is strict. It writes to a `.nc.tmp` sibling, **reopens the finished file without CF decoding** so the validators see exactly what is on disk, and refuses the product unless the conventions, the twelve-cell float64 time axis with its named bounds variable, a vertical axis that is genuinely the model's own (`air_pressure` in Pa with `positive = "down"` and `axis = "Z"`, finite, positive and free of repeated levels, or a named pressure field sharing the field's dimensions), the absence of the application grid, `lat` units, the presence of every processed variable, the statistic dtypes, `cell_methods`, units, dimension order and the absence of any per-variable `*_air_pressure` field all check out — only then is the temporary renamed over the destination, so a failed run never leaves a half-written or non-CF product. Because there is now one file per model, previously generated combined and per-variable products are obsolete and must be regenerated with `jumacs build`.

`jumacs application --model SOCOL --start-year 1985 --end-year 2014` validates the existing native CCMI and WACCM-X climatologies, remaps them to 124 pressure levels and 36 area-weighted latitude bands, and optionally blends WACCM-X above the CCMI top. It writes one validated NetCDF to `products/application/SOCOL/`; `--no-extension` writes the remapped CCMI product alone. Application fields retain the base model names and the four statistics `mean`, `sigma`, `minimum`, `maximum`; `n_years` remains in the native product.

`jumacs coverage --model MODEL` writes finite-value-based pressure limits, native geopotential-height ranges (where available), a representative median top height and level count per species to `products/diagnostics/coverage/MODEL/`. `jumacs compare --models GEOSCCM EMAC` writes original model fields, absolute and relative difference on a common pressure grid in the overlapping domain. Relative difference is `100 × (first − second) / second` and is undefined where the second field is zero. Interpolation is in log pressure and never extrapolates; `compare`/`evaluate` take their own query levels from `--pressure-hpa`, which is a report grid only and does not change the product axis — and because products are stored on native levels, that query grid is exactly where the two models are brought onto one vertical axis, with levels a model does not reach left missing there. `jumacs evaluate` accepts a separate evaluation NetCDF with the requested field and pressure coordinate, and produces difference, relative difference and RMS; it does not rank or adjust models. Plots from `quicklook`, `trends`, the model atlas and representative comparison maps are diagnostics only.

`jumacs coverage-matrix [--model all|auto|NAME,NAME] [--start-year --end-year]` answers a narrower question: for each **published product**, where that model has usable values and where WACCM-X has usable values, so it reads as a per-model readiness check for extending that model upward rather than as a multi-model consensus. It reads `products/climatology/...` only — never the raw or processed data — validates each file against the same contract the writer enforces (a product that already sits on the application grid is refused with a rebuild hint, never resampled), and starts from each field exactly as that model published it, on its own levels, mapping product fields back to the canonical species of `config/species.yaml` through each model configuration, and writes `products/comparison/coverage_matrix.csv`, `.md` and `.json` with one row per CCMI model and canonical variable; WACCM-X is the reference and never a row of its own. A finite-value mask of the field is then moved onto the 124-level application grid with the shared log-pressure interpolation and **no bridging across missing levels**, and the field itself is interpolated along the same path; an application level counts only where the mask reaches it, so coverage that is broken in the middle stays broken instead of being bridged by endpoints. The per-level evidence is on disk: `level_finite_fractions` for every application level, `levels_usable` and `levels_any_finite`, and a native record per field (`native_level_count`, `native_pressure_min_pa`/`native_pressure_max_pa` as the model publishes them, `grid_finite_fraction` after the move onto the application grid). A pressure level is *usable* where at least `coverage.usable_sample_fraction` (default 0.9) of its months and latitudes are finite, and the weaker *any finite* extent is reported beside it (`min_any_pressure_pa`/`max_any_pressure_pa` against `min_usable_pressure_pa`/`max_usable_pressure_pa`). The reported lower bound is `max_valid_pressure_pa` — the highest-pressure level holding *any* finite value — so a 1000 hPa level that terrain removes from part of the time-latitude grid is still shown as available; it is descriptive only. The upper bound `min_usable_pressure_pa` stays threshold-based, and overlap, `waccmx_extends_upward` and `extension_status` use the strict usable masks alone. `contiguous_usable` carries the mask evidence, and `overlap_*` marks the levels usable in both sources, while `waccmx_extends_upward` means WACCM-X is usable at lower pressure — higher altitude — than the top of the model's usable range. `extension_candidate` demands both that upward reach **and** at least `vertical.MINIMUM_OVERLAP_LEVELS` (2) usable levels in common, the fewest on which a transition can be defined: an overlap thinner than that is reported as `overlap_no_extension`, which is exactly what the extension stage refuses too, because the same constant is shared by `coverage` and `extension` so the readiness check can never promise a join that the joiner would decline. `coverage.usable_level_fraction` (default 0.5) only labels a field *broadly usable* and is not a condition for overlap or extension; both thresholds live in `config/climatology.yaml`, and `--usable-sample-fraction`/`--usable-level-fraction` override them for one run. `extension_status` is one of `not_applicable` (the model lacks the variable, or the field is two-dimensional such as `surface_pressure`), `mapping_unresolved` (no WACCM-X counterpart is configured and none is guessed), `no_waccmx_variable` (configured but absent from the WACCM-X product), `no_overlap`, `overlap_no_extension`, `extension_candidate`. Family sums (`Cly`, `Bry`, `NOy`) stay separate rows from their constituents, and the `coverage.application_focus` species get their own Markdown table while every other inventoried species remains in the CSV and JSON. CSV and JSON keep pressure in Pa, the Markdown shows hPa with a 7 km scale-height estimate (indicative only above about 80 km). The coverage matrix writes diagnostics only: no transition pressure, no weights, and no change to products.

The older, independent altitude-grid pipeline, `jumacs compact --model GEOSCCM` or `jumacs compact --model EMAC`, creates separate files in `products/climatology/combined/`. The default grid is monthly × altitude (0–120 km in 1 km steps) × latitude (85°S–85°N in 5° steps); longitude is absent because the source fields are zonal means. Fields are stored as compressed float32. The altitude axis is **geopotential height**, mapped from each source's monthly native geopotential-height profile; pressure-level chemistry is mapped using that model's pressure–height relation. Interpolation does not extrapolate below the lowest or above the highest valid native point, so the exact 0 km cell can be missing. Where both models provide a species, a raised-cosine transition spans 55–65 km. That band lies inside the checked overlap of the available fields; the command refuses an incomplete overlap. Source-variable names and `source_status` identify whether a field is blended or supplied by only one source. Species absent from WACCM-X remain missing above the CCMI valid top. A compact product is separate from the pressure-grid application product and from both native climatologies.

The compact file is a straightforward month/height/latitude input for a JuMACS-aware JURASSIC or MPTRAC adapter. The current MPTRAC `read_clim_zm()` interface expects **separate** pressure-grid files with `time,press,lat` and variable-specific names, so it cannot directly read this multi-variable altitude-grid file. A pressure-grid adapter and application-side integration still need validation before claiming plug-and-play use.

`docs/evaluation/` documents independent satellite comparisons (for example SPARC, SWOOSH, GOZCARDS, ACE-FTS, MIPAS or MLS). No satellite dataset is fetched by this project. Data and generated products are excluded from Git. The MIT licence covers project code; cite the CEDA datasets and follow their licences when using their data.

## Repository and mirror layout

`jumacs/` is both the Git root and the HPC working directory. Tracked material is limited to `src/`, `config/`, `tests/`, `docs/`, `scripts/`, and root metadata (`README.md`, `LICENSE`, `CITATION.cff`, `pyproject.toml`, `Makefile`, `.gitignore`). The full model files in `data/raw/`, monthly zonal series in `data/processed/`, generated scientific files in `products/`, and the static browser in `site/` are ignored by Git. `cache/` and `tmp/` are ignored work areas. The path defaults are documented in `config/jumacs.yaml` and resolved from the repository root. `products/release/` is reserved for explicitly selected public datasets; nothing is added automatically.

Generate the application-product browser **on the HPC system**, where the application NetCDF files and monthly zonal series are stored. The interactive page lets you select a model and variable, then switch between January/April/July/October cross sections, the twelve-month climatological annual cycle, and the original multi-year monthly time series where available. Line plots compare five area-weighted latitude bands at 1000, 100, 10 and 1 hPa, sampled by log-pressure interpolation. The command copies application NetCDF files into `site/products/application/`. The generated `site/` tree has only relative links and can be mirrored as one unit. Re-running the command replaces generated plots and copied application products, removing stale entries.

`jumacs inventory` inspects existing native and application climatologies and writes a searchable data-availability overview to `products/catalog/climatology_inventory.{csv,json,md}`. `jumacs browse` refreshes the same inventory before generating the website's **Data availability** view; the Markdown lists the current contents without maintaining a second hand-written inventory here.

```bash
cd /p/data1/slmet/model_data/jumacs
jumacs inventory
jumacs browse --start-year 1985 --end-year 2014
# Back in the local Git checkout:
make mirror-local
JUMACS_WEB_SITE_MIRROR=user@datapub.fz-juelich.de:/absolute/path/ make mirror-web
```

`make mirror-local` copies this complete `site/` tree, including its application NetCDF downloads, from the mounted HPC directory into the local checkout's ignored `site/`. Run `make mirror-web` from that local checkout with `JUMACS_WEB_SITE_MIRROR=user@datapub.fz-juelich.de:/absolute/path/` set to the chosen web destination. It refuses a site without the generated application-product tree. The older `make site` command serves the legacy quicklook/catalog page. JuMACS does not use GitHub Pages. See [docs/README.md](docs/README.md) for the directory map.
