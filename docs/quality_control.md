# Quality control and evaluation

## Post-download audit

After a transfer and before enabling any processing, run the offline post-download audit. It reads only local raw files and manifests — no CEDA access, no re-planning, no downloads, no config changes — and opens at most a few small representative files per model (metadata plus tiny slices; no hashing, no full-field reads):

```bash
jumacs validate-raw --model all       # transfer integrity: completeness, .part strays, signatures, readability
jumacs coordinate-audit --model all   # conventions: grid, vertical coordinate, time, reader compatibility
jumacs post-download-audit --model all  # both stages in one run
```

`validate-raw` reports per model `ok`, `incomplete`, `invalid`, `not_downloaded` or `not_applicable` (manifest vs. disk counts, leftover `.part` files, NetCDF/HDF5 signatures, time decoding, size tolerance against manifest listing estimates) and writes `products/diagnostics/raw_validation/MODEL.json` plus `products/comparison/raw_validation.{csv,md}`. `coordinate-audit` classifies each model's observed horizontal grid (regular, curvilinear, already zonal, partial longitude), vertical coordinate (pressure levels, hybrid sigma-pressure/hybrid height with observed vs. inferred `formula_terms`, pure sigma, altitude) and time handling, and grades reader compatibility `supported_now`, `small_mapping_change`, `reader_extension_needed` or `unsupported` with machine-readable reasons and a `main_action` per model; outputs are `products/diagnostics/coordinate_audit/MODEL.json` and `products/comparison/coordinate_audit.{csv,md}`. Treat `incomplete`/`invalid` or any `reader_extension_needed` as a gate: fix the transfer or extend the reader before submitting zonal/climatology jobs. The audit is descriptive evidence; it never edits `config/models/*.yaml` or enables processing steps.

## Coverage and comparison diagnostics

`jumacs coverage --model MODEL` writes finite-value-based pressure limits, native geopotential-height ranges (where available), a representative median top height and level count per species to `products/diagnostics/coverage/MODEL/`. `jumacs compare --models GEOSCCM EMAC` writes original model fields, absolute and relative difference on a common pressure grid in the overlapping domain. Relative difference is `100 × (first − second) / second` and is undefined where the second field is zero. Interpolation is in log pressure and never extrapolates; `compare`/`evaluate` take their own query levels from `--pressure-hpa`, which is a report grid only and does not change the product axis — and because products are stored on native levels, that query grid is exactly where the two models are brought onto one vertical axis, with levels a model does not reach left missing there. `jumacs evaluate` accepts a separate evaluation NetCDF with the requested field and pressure coordinate, and produces difference, relative difference and RMS; it does not rank or adjust models. Plots from `quicklook`, `trends`, the model atlas and representative comparison maps are diagnostics only.

`jumacs coverage-matrix [--model all|auto|NAME,NAME] [--start-year --end-year]` answers a narrower question: for each **published product**, where that model has usable values and where WACCM-X has usable values, so it reads as a per-model readiness check for extending that model upward rather than as a multi-model consensus. It reads `products/climatology/...` only — never the raw or processed data — validates each file against the same contract the writer enforces (a product that already sits on the application grid is refused with a rebuild hint, never resampled), and starts from each field exactly as that model published it, on its own levels, mapping product fields back to the canonical species of `config/species.yaml` through each model configuration, and writes `products/comparison/coverage_matrix.csv`, `.md` and `.json` with one row per CCMI model and canonical variable; WACCM-X is the reference and never a row of its own. A finite-value mask of the field is then moved onto the 124-level application grid with the shared log-pressure interpolation and **no bridging across missing levels**, and the field itself is interpolated along the same path; an application level counts only where the mask reaches it, so coverage that is broken in the middle stays broken instead of being bridged by endpoints. The per-level evidence is on disk: `level_finite_fractions` for every application level, `levels_usable` and `levels_any_finite`, and a native record per field (`native_level_count`, `native_pressure_min_pa`/`native_pressure_max_pa` as the model publishes them, `grid_finite_fraction` after the move onto the application grid). A pressure level is *usable* where at least `coverage.usable_sample_fraction` (default 0.9) of its months and latitudes are finite, and the weaker *any finite* extent is reported beside it (`min_any_pressure_pa`/`max_any_pressure_pa` against `min_usable_pressure_pa`/`max_usable_pressure_pa`). The reported lower bound is `max_valid_pressure_pa` — the highest-pressure level holding *any* finite value — so a 1000 hPa level that terrain removes from part of the time-latitude grid is still shown as available; it is descriptive only. The upper bound `min_usable_pressure_pa` stays threshold-based, and overlap, `waccmx_extends_upward` and `extension_status` use the strict usable masks alone. `contiguous_usable` carries the mask evidence, and `overlap_*` marks the levels usable in both sources, while `waccmx_extends_upward` means WACCM-X is usable at lower pressure — higher altitude — than the top of the model's usable range. `extension_candidate` demands both that upward reach **and** at least `vertical.MINIMUM_OVERLAP_LEVELS` (2) usable levels in common, the fewest on which a transition can be defined: an overlap thinner than that is reported as `overlap_no_extension`, which is exactly what the extension stage refuses too, because the same constant is shared by `coverage` and `extension` so the readiness check can never promise a join that the joiner would decline. `coverage.usable_level_fraction` (default 0.5) only labels a field *broadly usable* and is not a condition for overlap or extension; both thresholds live in `config/climatology.yaml`, and `--usable-sample-fraction`/`--usable-level-fraction` override them for one run. `extension_status` is one of `not_applicable` (the model lacks the variable, or the field is two-dimensional such as `surface_pressure`), `mapping_unresolved` (no WACCM-X counterpart is configured and none is guessed), `no_waccmx_variable` (configured but absent from the WACCM-X product), `no_overlap`, `overlap_no_extension`, `extension_candidate`. Family sums (`Cly`, `Bry`, `NOy`) stay separate rows from their constituents, and the `coverage.application_focus` species get their own Markdown table while every other inventoried species remains in the CSV and JSON. CSV and JSON keep pressure in Pa, the Markdown shows hPa with a 7 km scale-height estimate (indicative only above about 80 km). The coverage matrix writes diagnostics only: no transition pressure, no weights, and no change to products.

## Evaluation data

Satellite climatologies and observations are independent evaluation sources, never inputs to the primary JuMACS climatology. They must not fill gaps, correct model biases, normalize trends, or select a model automatically. Independent satellite comparisons use sources such as SPARC, SWOOSH, GOZCARDS, ACE-FTS, MIPAS and MLS; no satellite datasets are fetched by this project. Store generated machine-readable evaluation results under `products/comparison/evaluation/` and any browser plots under `site/`. The `jumacs evaluate` command compares compatible fields on an overlapping month, latitude and pressure domain. Retain each source's provenance and licence.
